## 1. Design decision: (a), per-tick jsonb-array spec

Per the Database Engineer brief's two options, went with **(a)**: the 71-row catalog (which stats,
ramp/decay/one-shot, cap, disable condition) stays entirely **client-side** in
`signature-abilities.ts`; the tick RPCs receive the **resolved spec for the firing ability** as
arguments each call and own only the state machine (counters, netByStat bookkeeping, ±3/±cap clamps,
revert, decay, re-arm, replay). No server-side spec table.

`_stat_specs` is a **jsonb array** mirroring stub §2 `StatChangeSpec[]` verbatim (Backend passes the
catalog row's `stat` array with **no reshaping**) — not the flat-scalar example in the original brief,
because a `SignatureEngineSpec.stat` is an array and multi-stat rows (Kyogre, Rayquaza, Xerneas,
Zygarde-fallback, Registeel/Phione ramp pairs) can't be expressed one-per-call without tripping the
per-side replay guard on a second call:

```json
[{ "mode": "ramp", "stat": "attack", "target": "self", "perCorrect": 1 }]
[{ "mode": "ramp", "stat": "attack", "target": "self", "perCorrect": 1 },
 { "mode": "ramp", "stat": "crit",   "target": "self", "perCorrect": 1 },
 { "mode": "ramp", "stat": "speed",  "target": "self", "perCorrect": 1 }]   // Kyogre #17
[{ "mode": "decay", "stat": "attack", "target": "self", "initial": -2, "perQuestion": -1, "floor": -3 }]
[{ "mode": "one_shot", "stat": "defense", "target": "opponent", "delta": -2 }]
```

**R1 — every stat is tracked and reverts together.** The earlier M1 "only `[0]` tracked" limitation
is gone. `SigRuntimeEntry.netDelta` (scalar) is replaced by **`netByStat: Record<string, number>`**
keyed by **`"<target>:<stat>"`** — `target ∈ {self, opponent}`, `stat ∈ {attack, defense, speed,
crit}` (never `"random"`: a random one-shot's actually-changed cell is detected and stored under its
resolved stat key). Examples: `"self:attack"`, `"opponent:speed"`. Each key's value is the signed
stage delta THIS ability contributed to that (side, stat) cell of the shared `*_stages` map. On the
disable/incorrect revert, the helper loops **all** keys and subtracts each from the correct stat on
the correct side, so a multi-stat ability reverts entirely at once (owner ruling 1). `stacks` stays a
single scalar — the shared ramp counter; all ramp stats in a row advance one increment per armed
correct answer, capped at `SIG_STACK_CAP` increments, with the +3 magnitude cap enforced per stat.

> **@Coordinator — confirm this in the stub:** `SigRuntimeEntry.netDelta: number` →
> `netByStat: Record<string, number>`; key format exactly `"<target>:<stat>"` (lower-case,
> single colon, no spaces), target one of `self|opponent`, stat one of `attack|defense|speed|crit`.
> `stacks` remains `number` (shared ramp counter). All other `SigRuntimeEntry` fields unchanged.

## 2. `pvp_sig_engine_tick` — final signature (human self-tick)

```sql
pvp_sig_engine_tick(
  _match_id uuid,
  _question_index int,         -- 0-indexed, exactly as the client loop passes it (F1)
  _pokemon_id int,              -- caller's own authorized ability id (own partner, or Mew's resolved transform)
  _correct boolean,
  _trigger_fired boolean,       -- client-evaluated deterministic predicate (site="client", stub §1)
  _stat_specs jsonb default '[]'::jsonb,        -- StatChangeSpec[] (stub §2), see §1
  _disable_kind text default 'none',            -- DisableSpec.kind (stub §3) resolved for this ability
  _disable_n int default 0,                     -- DisableSpec.n where the kind takes one
  _disable_next_question boolean default false, -- true only for kind = disable_next_question_after_effect
  _stack_cap int default 3                      -- SIG_STACK_CAP; per-ability ramp ceiling, not the ±3 global clamp
) returns jsonb
```

Returns `SigEngineTickResult` (stub §9): `{ ok, hostStages, guestStages, hostSigRuntime,
guestSigRuntime, noop?, reason? }`. `noop:true, reason:'stale'` on replay. Errors:
`{ok:false, error: 'no_session'|'not_found'|'forbidden'|'not_active'|'unauthorized_ability'}`.
Acting side derived from `auth.uid` (host vs guest); mutates that side's `*_sig_runtime` +
`*_sig_engine_last_idx`.

**`_disable_kind` values understood:** `revert_stat_after_incorrect` ·
`disable_increase_after_incorrect` · `disable_effect_after_incorrect` · `once_per_battle` · `none`.
`disable_multiplier_after_incorrect` (client-side, damage-calc — Articuno) and
`disable_healing_after_questions` (bespoke, Suicune) are **not** handled here; pass `'none'`.
`disable_next_question_after_effect` is the separate boolean `_disable_next_question` (composes with
any kind — Mewtwo/Entei/Jirachi). `any_of` (Moltres) is **not** a single `_disable_kind` — resolve
the currently-binding sub-condition client-side, or keep that row on the existing `sig_state` phase.

## 2b. `pvp_bot_sig_engine_tick` — HOST drives the bot/guest side (R3)

```sql
pvp_bot_sig_engine_tick( <identical 10-arg shape to pvp_sig_engine_tick> ) returns jsonb
```

**Why it exists:** in a bot match the guest is a bot with no `auth.uid`; the HOST's session drives its
moves. `pvp_sig_engine_tick` resolves the acting side FROM `auth.uid`, so the host calling it would
tick the host's own runtime (or fail `unauthorized_ability` on the bot's dex). This RPC is the
sig-engine analogue of `apply_bot_pvp_signature_effect`.

**Auth model (mirrors `apply_bot_pvp_signature_effect`, 20260706202620:254-269):** caller must be
`host_id` AND `is_bot_match = true` AND match active; otherwise `forbidden` / `not_bot_match` /
`not_active`. **Acting side is fixed to the GUEST** (the bot) — it treats `guest_stages` as self,
`host_stages` as opponent, and mutates `guest_sig_runtime` + `guest_sig_engine_last_idx`. Ownership:
`_pokemon_id` must equal the bot's authorized id — `guest_partner_id`, or `guest_transform_id` when
the bot is Mew(151) (the guest analogue of the human tick's transform resolution; a mild superset of
`apply_bot_pvp_signature_effect`, which checks only `guest_partner_id` — flagged for QA below). No
partner self-heal (apply_bot doesn't do one either). Same return shape as `pvp_sig_engine_tick`.

**Shared-lifecycle factoring (R3):** both tick RPCs do only auth + side/ownership resolution, then
`return public._pvp_sig_engine_apply(_match_id, _i_am_host, …)`. `_pvp_sig_engine_apply` is an
internal SECURITY DEFINER function holding the entire §3 lifecycle (replay guard → counters →
revert/disable → re-arm → decay → ramp → one_shot → next-q skip → persist) EXACTLY ONCE — no
human/bot drift. It has no auth of its own, so it is `REVOKE ALL … FROM PUBLIC`: only the two tick
RPCs (running as the function owner, which retains owner EXECUTE) can invoke it; a direct
`authenticated` call is refused. QA: there is a single lifecycle body to test, exercised via both
entry points.

## 3. Backend call mapping (`src/lib/pvp-live.ts` `sigEngineTick`; `src/lib/pvp-bot.ts` `botSigEngineTick`)

Called **once per side per answer**. Human side → `pvp_sig_engine_tick`; bot/guest side (host session)
→ `pvp_bot_sig_engine_tick`. Same arg resolution for both; only the RPC name differs.

| Stub field | RPC arg |
|--|--|
| `spec.stat` (array) | `_stat_specs` — pass as-is (jsonb) |
| `spec.disable.kind` | `_disable_kind` (`'none'` if `any_of`/multiplier/healing-disable — see §2) |
| `spec.disable.n` (where present) | `_disable_n` |
| `spec.disable.kind === 'disable_next_question_after_effect'` | `_disable_next_question = true`, `_disable_kind = 'none'` |
| `SIG_STACK_CAP` (stub, = 3) | `_stack_cap` (override only if a future row needs a non-3 cap) |
| loop's 0-indexed question | `_question_index` (do not pre-increment) |
| `hitTriggerHolds`/`postTriggerFires` | `_trigger_fired` |
| answer correctness | `_correct` |

Call for **every** answer even with `_stat_specs: []` — `consecutiveWrong`/`firedThisBattle`/
`disabled` bookkeeping is generic and gates bespoke effects applied elsewhere. Surface `ok:false` as a
sonner toast (COMMON_RULES §2); `noop:true` is not an error.

## 5. Function inventory (exact signatures)

```sql
-- pure jsonb helpers (language plpgsql immutable; no grant — same style as _pvp_bump_stage)
_pvp_bump_stage_tracked(_stages jsonb, _runtime jsonb, _dex text, _target text, _stat text, _per_fire int, _cap int) returns jsonb
  -- {stages, runtime}. Ramp-applies ONE stat: min(|_per_fire|, _cap - |netByStat["_target:_stat"]|)
  -- signed, via _pvp_bump_stage (±3 clamp); accumulates the actual clamped delta into that slot.
  -- Does NOT touch `stacks`.

_pvp_revert_ability_stat(_self_stages jsonb, _opp_stages jsonb, _runtime jsonb, _dex text) returns jsonb
  -- {selfStages, oppStages, runtime}. Loops ALL netByStat keys, subtracts each from the correct
  -- stat on self/opp; clears netByStat + zeroes stacks. NOTE: signature differs from BOTH the
  -- architecture-doc 3-arg summary AND the earlier draft — it now takes BOTH stage maps (R1: a
  -- multi-stat ability may hold self AND opponent contributions that must revert in one pass).

-- internal lifecycle body (SECURITY DEFINER, set search_path=public, REVOKE ALL FROM PUBLIC)
_pvp_sig_engine_apply(_match_id uuid, _i_am_host boolean, _question_index int, _pokemon_id int,
  _correct boolean, _trigger_fired boolean, _stat_specs jsonb, _disable_kind text, _disable_n int,
  _disable_next_question boolean, _stack_cap int) returns jsonb
  -- The whole §3 lifecycle for the side chosen by _i_am_host. Assumes caller validated
  -- session/active/ownership and holds the FOR UPDATE lock. Callable ONLY by the two tick RPCs.

-- public entry points (SECURITY DEFINER, set search_path=public, grant execute to authenticated)
pvp_sig_engine_tick(...10 args...) returns jsonb           -- §2 (human, side from auth.uid)
pvp_bot_sig_engine_tick(...10 args...) returns jsonb       -- §2b (host drives guest/bot)
```

## 6. What changed in the two effect RPCs (R2)

Both via `CREATE OR REPLACE` in this migration (never edited a shipped file). **Removed from BOTH:**
the `stat_scale` branch — the only incremental/scaling stat path in either function
(`floor(_scale_count/per)` capped at `max`, re-applied via `_pvp_bump_stage` every call). This is the
R2 double-writer risk: the sig-engine tick now owns all ramp/decay netByStat bookkeeping, and a
second uncoordinated writer would desync each ability's tracked contribution from the shared stage.

- **`apply_pvp_signature_effect`** (human): `stat_scale` `elsif` folded into the final `else`
  no-op. Body otherwise byte-for-byte identical to `20260706130000`. Kept: ownership auth,
  `sig_state` phase, suppression / weather-negation / weather-non-owner, `post_answer` replay cursor
  (`*_post_answer_last_idx`, its own cursor — untouched), `battle_start`/`manual` gating, and kinds
  `stat_stage` (fixed one-shot delta — Zekrom, Regice, Raikou, Deoxys/Magearna recoil, …), `status`
  (chance-gated), `cure`, `heal`, `drain`, `suppress_ability`, `swap_stages`, `cleanse`.
- **`apply_bot_pvp_signature_effect`** (bot, `20260706202620:230`): its own `stat_scale` branch
  removed; the function already had a trailing `else` no-op for exotic kinds, so `stat_scale` rows now
  fall into it. Everything else byte-for-byte identical. `CREATE OR REPLACE` preserves the existing
  EXECUTE grant (that migration had no in-file grant).

**Known gap for Frontend:** `pokemon_id 1016` is the only catalog row using `stat_scale` today
(`battle_start`, `attack`, `per=25/max=3`); after this migration it silently no-ops in BOTH effect
RPCs until re-authored onto the tick's ramp/decay lifecycle (`_stat_specs`).

## 7. Type-ability isolation (F6/R1) — confirmed untouched

`20260709120000_pvp_type_abilities.sql` (`apply_pvp_type_ability_effect`, `host/guest_ability_id`,
`host/guest_type_ability_started`) is a fully independent RPC/cursor/column set. Nothing here reads,
writes, or shares state with it. Cursors: `*_post_answer_last_idx` (signature bespoke/one-shot),
`*_sig_engine_last_idx` (new, this migration), `*_type_ability_started` (type-ability) — three
parallel systems, never cross-wired.
