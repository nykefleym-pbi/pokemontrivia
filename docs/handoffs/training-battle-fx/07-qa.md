## 1. How to read this checklist

- **Opponent = the bot** in Training / Nearby Battle. `self` cues are from the local player's POV.
- Run every scenario in a **live Training battle on the Vercel preview** (realtime + sonner).
- **Toasts funnel through one path** (`useBattleFxCues`) for both sides — the exact strings below
  are the frozen wording from that hook. Verify the string **and** the toast **level/colour**
  (info / success / warning / error) **and** any on-sprite visual.
- Placeholders: `{name}` item/move name, `{effect}` short effect line, `{note}` ability note.
- Cues in one slot are released **staggered ~350 ms apart** in a fixed order
  (answer-result → item → type-ability → signature → status-expired → status-applied) — a burst
  should read as a legible sequence, **never** a simultaneous stack or a lost toast (Story 7).

## 2. Setup / preconditions

1. Open the Vercel preview build of this branch; sign in.
2. Start a **Training** (or Nearby) battle so the opponent is a **bot** (partner is always
   Legendary/Mythical — the bot therefore has a **signature** ability and **never** a plain type
   ability; see §3 Story 3).
3. Have a bag with at least one **healing item** (e.g. Super Potion) and, if testing berries, an
   **offensive berry** (`berry.target === "opponent"`).
4. Keep the toast area visible; do not dismiss toasts so ordering can be observed.

## 3. Story-by-story manual checklist (Stories 1–6)

### Story 1 — Effects actually resolve (correctness)
**Given** a type ability's trigger condition is met (use a partner whose type ability has a
runtime trigger), **When** the slot resolves, **Then** the effect is reflected in state
(HP / score / stat stage / status chip) for the correct side — not just a toast.
- **Self type ability fires:** on the qualifying slot, expect the state change **and** a
  **success** toast: `⚡ Your {name} — {note}` (`— affects them!` appended if it hits the bot).
- **Confused after 2 consecutive wrong** is verified in **§7.3-B** (tricky).
- **Status tick/expire:** any applied status must tick down and clear per its rules; confirm the
  chip count decreases and clears, with the matching expiry cue (§ Story 4).
- **Bot type ability:** N/A — the bot is always Legendary/Mythical, so it never has a plain type
  ability. Do not expect a `⚡ Opponent's …` type-ability cue in Training.

### Story 2 — Item usage is announced
**Given** the local player uses an item, **Then**:
- **Self, self-targeted (heal/buff):** **info** toast `{emoji} You used {name} — {effect}`.
- **Self, offensive berry (hits bot):** **success** toast
  `{emoji} You used {name} on the opponent — {effect}`.
- Plus SFX (`item_use`) and the HP/stat change on the bars.

**Given** the **bot** uses an item (see §7.3-A to force it), **Then**:
- **Opponent, self-targeted (heal):** **info** toast `{emoji} Opponent used {name} — {effect}`.
- **Opponent, offensive berry (hits you):** **warning** toast
  `{emoji} Opponent used {name} — affects YOU! {effect}`.
- Attribution and clarity must match the self cue (parity, Story 7).

### Story 3 — Type ability activation is announced
**Given** the **local player's** type ability activates, **Then** a **success** toast
`⚡ Your {name} — {note}` (with `— affects them!` if it lands on the bot), fired **once per battle**
for a conditional fire-note ability, plus the state change.
- **Bot side:** N/A in Training (bot has no type ability — see Story 1). If ever a non-legendary
  opponent appears, its cue is a **warning** `⚡ Opponent's {name} — {note} — affects YOU!/them!`.

### Story 4 — Status changes are announced
**Given** any status (poison, burn, paralysis, sleep, freeze, badly-poisoned) is **applied** to a
side via any source (item, ability, weather), **Then** a cue fires from the status **diff** watcher:
- **Self applied:** **warning** `{emoji} You're {label-lower}!` + ` ({n} questions)` when duration known.
- **Opponent applied:** **success** `{emoji} Opponent is {label-lower}! ({n} questions)`.
**Given** a status **expires/clears**, **Then**:
- **Self expired:** **success** `{emoji} You're no longer {label-lower}.`
- **Opponent expired:** **info** `{emoji} Opponent is no longer {label-lower}.`
- Confirm the status **chip** appears on apply and disappears on expiry, matching the toast.
- **Note:** `confused` is **excluded** from this diff watcher (it is client-authoritative and cued
  directly by apply/tick-out — see §7.3-B) so it is never double-announced.

### Story 5 — Signature ability activation is announced
**Given** the **local player's** signature ability triggers (battle-start auto-fire and/or manual
unleash and/or post-answer), **Then** a **success** toast `✨ {move} — {desc}!`
(or `✨ {move} activates!` when no description), plus the state change and `item_use` SFX.
**Given** the **bot's** signature fires (frequent at battle start; post-answer is aggression-gated —
see §7.3-A), **Then** a **warning** toast
`✨ Opponent's {move} — {desc} — affects YOU!` (or `— affects them!`), attributing it to the bot.
- Verify identity is present (move name + effect), not a silent HP change.

### Story 6 — No answer counts as incorrect
Full procedure in **§7.3-C** (tricky — this is the race the fix targets).
- **Given** the **local player** lets the slot time out at **default speed** with nothing selected,
  **When** the slot resolves, **Then** an **error** toast `⏱️ No answer — counted incorrect.`
  fires, the slot is scored **incorrect** (HP chip taken, streak reset), and it **counts toward the
  2-wrong confused trigger** (chain into §7.3-B).
- **Opponent no-answer cue** (`⏱️ Opponent didn't answer — counted incorrect.`, **info**) exists in
  the hook but the Training bot **always submits a move**, so it is **not expected to fire** in
  Training. Flag if you ever see it (would indicate the bot failed to submit).

## 4. Tricky scenarios (architecture-flagged) — §7.3

### 7.3-A — Force the bot's rare item & signature cues (Stories 2, 5)
The bot only uses an item when its **HP ≤ 45%**, and its post-answer signature is **aggression-gated**
— so "silence" here is usually **rarity, not breakage** (arch §1 #2/#5). To force delivery:
1. Play aggressively / use offensive effects to drive the **bot's HP below 45%**.
2. Continue slots; on a bot heal expect the **opponent item cue** (Story 2 opponent).
3. Over several correct bot answers, expect at least one **opponent signature cue** (Story 5 opponent);
   the **battle-start** signature should also fire once early.
- **Pass:** both cues appear with correct attribution and effect text, at parity with self cues.
- **If never seen after sustained pressure:** record for Frontend as a possible realtime-delivery
  failure (vs rarity) — note the match id and whether the HP/state change happened *without* a toast.

### 7.3-B — Confused after 2 consecutive wrong, incl. a no-answer (Stories 1 & 4)
1. **Self:** answer **wrong twice in a row** (a no-answer from §7.3-C counts as one).
   - On the **2nd** consecutive wrong: expect **warning** `🌀 You're confused! (2 questions)`, the
     **confused chip** on your panel, and the **confusion sprite overlay**.
2. On a subsequent **correct** answer there is a **25% chance** the attack "misses":
   toast `🌀 Confused — your attack missed!` and one confused tick consumed.
3. After the confused ticks drain to 0: expect **success** `🌀 You're no longer confused.` and the
   chip/overlay clears.
4. **A single correct answer resets the wrong-streak** — verify wrong→correct→wrong does **not**
   confuse (no death-spiral).
5. **Bot:** make the **bot** answer wrong twice consecutively (needs a low-accuracy bot / unlucky
   streak) → expect **success** `🌀 Opponent is confused! (2 questions)` + the bot's confused
   overlay; its confused ticks are simulated client-side (`botConfusionMiss`, unit-covered).
- **Pass:** confused applies on exactly the 2nd consecutive wrong, is visible (chip + overlay), and
  clears with the expiry cue; it is **never** double-announced by the Story 4 status watcher.

### 7.3-C — No-answer at default speed = incorrect (Story 6)
This reproduces the exact race the fix targets (personal-timeout vs wall-clock ceiling at equal
default deadlines).
1. Ensure **no speed modifier** is active (default timer = full slot).
2. On a slot, **select nothing** and let the timer run fully out.
3. **When** the slot advances, **Then**:
   - **error** toast `⏱️ No answer — counted incorrect.`;
   - your side is **scored incorrect** (wrong-answer HP chip applied, streak reset to 0) —
     identical to an actively wrong answer;
   - the slot is resolved **exactly once** (no double HP hit) — the ceiling resolve and the
     personal-timeout submit must not both fire (guarded by `lastResolvedIdxRef`);
   - it **increments the consecutive-wrong counter** → do it twice to chain into **§7.3-B** confused.
- **Pass:** every default-speed no-answer scores incorrect and feeds confused. **Fail (record for
  Frontend):** slot skipped with no score / no toast, or a doubled HP hit.

## 5. Human-vs-human PvP regression smoke (Story 7 / no regression)
The `emit` path is shared, so confirm the **reference** (human PvP) cues are unchanged.
1. Start a **live human-vs-human** PvP match (two clients / two accounts).
2. Trigger and verify each still works with the same wording/level as before:
   - **item** used by each side (self info/success; opponent info/warning);
   - **signature** ability (self success; opponent warning with identity);
   - **type ability** for a **non-legendary** partner (self success; opponent warning) — this is the
     path the bot lacks, so it must still fire human-vs-human;
   - **status** apply/expire cues (Story 4).
3. Confirm **no confused-after-2-wrong** behaviour leaks where it shouldn't and no doubled/lost
   toasts in a multi-effect slot.
- **Pass:** human-PvP cues identical to pre-change; no new confused/no-answer regressions.
